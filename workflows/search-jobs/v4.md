# search-jobs Workflow (v4)

Searches Google Jobs via SearchAPI, deduplicates results via `check_position_seen` (OB1) or `ingested-positions.csv` (local), fetches full JDs, and delegates per-job processing to `process-jd`. Fit jobs are saved as application stubs — **no auto-generated resumes**. Triggered by `/ingest <profile>`.

All file access follows the storage-routing policy (`DATA_BACKEND` env var).

**Changes from v3:**
- Step 1: After loading `PROFILES-QUICK-REFERENCE.md`, look up the profile in the `## Location Modes` table. Store as `location_mode`; default `"us-only"` if not found.
- Step 3: Outer loop over location passes (1 or 2 based on `location_mode`); inner loop over `sub_queries`. Remote pass appends ` remote` to each `current_query`. `--location` flag passed to `search-jobs.py`. Cross-pass deduplication handled by `check_position_seen` (OB1) or in-memory set (local).
- Step 3c-pre: Snippet pre-screen added — before JD fetch, check company name, title, and description snippet for obvious non-tech signals. Skip fetch for clear non-fits.
- Summary `## Sub-queries` section now lists location passes alongside sub-query terms.

**Changes from v1 (carried from v3):**
- Dedup moved from `seen-jobs.json` (Python script) to `check_position_seen` MCP tool (OB1) or `ingested-positions.csv` (local). Script no longer has file-based dedup or a `--no-dedup` flag.
- Every position encountered is logged to `js_ingested_positions` (OB1) or appended to `ingested-positions.csv` (local).
- Summary `.md` is still generated and uploaded to OB1 (`summary_key` is stored in `js_search_runs`). This enables human review and backfill.
- Repost detection: positions seen >60 days ago are flagged and included in run summary.

**Changes from v2 (carried from v3):**
- `log_search_run` moved from Step 4b to Step 2 so `search_run_id` is valid before the processing loop; Step 4b now calls `update_search_run` to patch in final counters and `summary_key`.
- Step 3c-ii: prior-assessment gate — `search_thoughts` lookup for `seen=false` positions; skips fetch if a fresh fit assessment exists (< 30 days).
- JD content handling rule added (Step 3e): prohibits writing `full_jd_content` to temp files mid-loop.
- Raw data rule added (Phase 3-FETCH): prohibits per-company raw JSON files; all raw analysis must run in subprocesses.
- Do-not-re-read guard added to Step 1 pre-load block.

## Location mode semantics

These semantics are defined here (no applicant-specific values hardcoded). All location strings are read at runtime from `## Location Check` in `PROFILES-QUICK-REFERENCE.md`.

- **`us-only`**: single pass. `--location "United States"` (current default behavior).
- **`bay-area-plus-remote`**: two passes per sub-query:
  - Pass 1 (onsite): Read the hybrid/onsite-accepted location value from `## Location Check` in `PROFILES-QUICK-REFERENCE.md`. Use as `--location "<onsite-accepted-location>"`. Query is unchanged.
  - Pass 2 (remote): `--location "United States"`. Append ` remote` to each `current_query` before passing to the script.

The workflow derives the onsite location string by reading `## Location Check` verbatim and extracting the location labeled `✅` under "Hybrid/Onsite in..." — no hardcoded place names in this spec.

## Step 1 — Load Context

- Read `$APP_DIR/.env`; resolve `$APP_DIR`, `$APPLICANT_DIR`, `SEARCHAPI_KEY`, `SEARCH_TARGET_FITS` (default 10), `SEARCH_BATCH_SIZE` (default 10), `PLAYWRIGHT_PYTHON`, `DATA_BACKEND`
- If `SEARCHAPI_KEY` is not set: tell the user to add it and stop
- Parse invocation arguments: `--fits N` overrides `SEARCH_TARGET_FITS`; `--batch N` overrides `SEARCH_BATCH_SIZE`
- Load `applicant.md` for location/comp hard-stops:
  - OB1: `get_file('applicant.md')`
  - Local: read `$APPLICANT_DIR/applicant.md`
- Load `PROFILES-QUICK-REFERENCE.md`:
  - OB1: `get_file('profiles/PROFILES-QUICK-REFERENCE.md')`
  - Local: read `$APPLICANT_DIR/profiles/PROFILES-QUICK-REFERENCE.md`
- Confirm the profile exists and has at least one row in the `## Search Queries` table
- Extract ALL rows for this profile from `## Search Queries` into ordered list `sub_queries` (2–3 rows per profile)
- **Location mode detection:** Look up the current profile slug in `## Location Modes`. If a row is found, store `location_mode = <Mode value>`; else `location_mode = "us-only"`.
- If no profile argument: derive profile slugs from PROFILES-QUICK-REFERENCE.md and ask the user to choose one

Pre-extract and cache for reuse across all jobs:
- From `applicant.md`: "Location" section, "Deal-breakers (Hard No)" section, compensation/target salary line
- From `PROFILES-QUICK-REFERENCE.md`: `## Hard Stops` section, `## Location Check` section (used both for snippet pre-screen context and for deriving onsite location strings in bay-area-plus-remote mode)

**If `location_mode = "bay-area-plus-remote"`:** Extract the onsite-accepted location value from `## Location Check` now (the location labeled `✅` under "Hybrid/Onsite in..."). Store as `onsite_location`. This value is used as the `--location` argument in Pass 1. No hardcoded place names in this workflow.

**Pre-load workflow companions** (run in parallel with the PROFILES-QUICK-REFERENCE.md load above):
- Read `$APP_DIR/workflows/process-jd/draft.md` if it exists, else `$APP_DIR/workflows/process-jd/v4.md`
- Read the pinned storage-routing policy version (check `$APP_DIR/policies/storage-routing/skill.yaml` for the pinned version, then read that file)
- OB1: `get_file('memory/applicant-setup-status.md')`

These documents are re-read after every auto-compaction event during long ingest runs. Loading them here puts them in the cache prefix for the entire session. `applicant-setup-status.md` is auto-generated (Stop hook) and Claude never writes it — loading it once prevents repeated `rest:GET /api/v2/files/memory/applicant-setup-status.md` calls.

**Do not re-read this document mid-session.** All instructions needed for this run are loaded here. If a question arises about tool signatures or endpoint behavior during the run, use ToolSearch — do NOT grep this file or inspect `job-search-server.ts` / `job-search-tools.ts`.

**Local mode only — load dedup table:**
Read `$APPLICANT_DIR/search/ingested-positions.csv` into memory as an in-memory lookup set. If the file does not exist, start with an empty set.

## Step 3 — Two-Phase Execution

### Phase 3-FETCH — Fetch All Pages for All Location Passes and Sub-queries

**Raw data rule:** `$batch_file` is the sole source of truth for search results. Do NOT write individual per-company raw JSON files (e.g., `/tmp/raw-<company>.json`). Do NOT `cat` raw JSON payloads into context for inspection or deduplication analysis. Any multi-job analysis (dedup, scoring, summarization) must run inside a Python subprocess; emit only the structured output (scored list, summary table, or count) back to context.

**Determine location passes** from `location_mode`:
- `us-only`: `location_passes = [{"location": "United States", "remote_suffix": false}]`
- `bay-area-plus-remote`: `location_passes = [{"location": onsite_location, "remote_suffix": false}, {"location": "United States", "remote_suffix": true}]`

**Outer loop** over `location_passes`. For each `pass`:

**Inner loop** over each entry in `sub_queries`. For each `current_query`:

If `pass.remote_suffix` is true: use `query_for_api = current_query + " remote"`. Else: `query_for_api = current_query`.

**3a.** Set `page_token = null` for this sub-query/pass combination.

**3b. Pagination loop** (repeat until no more pages for this sub-query):

3b-i. Run the search script:
```bash
"$PLAYWRIGHT_PYTHON" "$APP_DIR/scripts/search-jobs.py" <profile> --query "<query_for_api>" --batch-out "$batch_file" --location "<pass.location>" [--page-token <token>] [--batch-size <SEARCH_BATCH_SIZE> if overridden]
```
Parse stdout as JSON. On exit code 1: report the error and stop.

3b-ii. Update counters: `pages_fetched += 1`, `total_results += total_fetched`.

3b-iii. Set `page_token = next_page_token` from script output. If null: break inner loop (sub-query exhausted).

Always run all sub-queries and all location passes in full — no early exit across sub-queries or passes.

### Phase 3-PROCESS — Dedup, Fetch Full JD, and Process Each Job

If batch file is empty (no jobs returned): output "No jobs returned from search." and proceed to Step 4.

Read the batch file line by line (NDJSON). **For each job object:**

**Compact guidance:** After every 10 positions processed in this loop, if no manual `/compact` has been run recently, use `/compact` to flush accumulated JD text from context. Each full JD adds 1,000–5,000 tokens; without periodic compaction, auto-compaction fires at unpredictable points, busts the cache prefix, and triggers re-reads of all companion docs loaded in Step 1.

**3c. Dedup check:**

Extract `candidate_urls` from `raw.apply_links[].link` and `apply_link` (may be empty).

- **OB1:** Call `check_position_seen(source_url=<first candidate_url or null>, company_name=<raw.company_name or null>, role_title=<raw.title or null>)`
  - **Null-literal rule:** When `raw.company_name` or `raw.title` is absent, undefined, or empty, pass the JSON literal `null` — never omit the value or leave it blank. Sending `{"company_name": , "role_title": }` is invalid JSON and will cause an InputValidationError on every call.
  - `seen=true AND is_repost=false`: call `log_ingested_position(..., outcome='duplicate', search_run_id=<search_run_id>)`, increment `duplicate_count`, output `= <Company> — <Role> [already seen]`, continue to next job
  - `seen=true AND is_repost=true`: call `log_ingested_position(..., outcome='duplicate', is_repost=true, first_seen_at=<result.first_seen_at>, search_run_id=<search_run_id>)`, increment `duplicate_count` and `repost_count`, append to `repost_jobs`, output `~ <Company> — <Role> [repost — first seen <first_seen_at>]`, continue to next job
  - `seen=false`: continue to Step 3c-ii below

**3c-ii. Prior-assessment gate (OB1 only, `seen=false` positions):**

Call `search_thoughts(query=<company_name + " " + role_title>, filters={metadata: {thought_category: "fit_assessment"}}, limit=1)`.

- **Result found AND `thought.created_at` within 30 days of today:**
  - Extract score and verdict from thought content.
  - Call `log_ingested_position(source_url=<first candidate_url or null>, company_name=<company>, role_title=<role>, profile_slug=<profile>, search_run_id=<search_run_id>, outcome='duplicate', no_fit_reason='prior assessment within 30 days — <verdict>, score <N>')`.
  - Increment `duplicate_count`.
  - Output: `= <Company> — <Role> [prior assessment <N> days ago — <verdict>, score N/10]`
  - Continue to next job. Do NOT fetch the URL.

- **No result, or result older than 30 days:**
  - Continue to Step 3c-pre (snippet pre-screen).
  - If a stale result exists (>30 days): append `[re-screening — prior assessment >30 days old]` to the console output line when the job is logged in Step 3g.

- **Local mode:** Skip this sub-step entirely — proceed directly to Step 3c-pre.

- **Local:** Check in-memory dedup set for: (1) URL exact match, (2) `lower(company):lower(role)` exact match
  - Match found: append `source_url,company_name,role_title,<profile>,duplicate,,false,,<now_iso>` to CSV, increment `duplicate_count`, output `= <Company> — <Role> [already seen]`, continue to next job
  - No match: continue below

**3c-pre. Snippet pre-screen** (non-duplicate, `seen=false` positions):

Before attempting JD fetch, inspect `raw.company_name`, `raw.title`, and `raw.description` snippet together. If the company name, job title, and description snippet together clearly signal a non-tech industry with no plausible fit to any active profile, mark as snippet-screened and skip:

- Call `log_ingested_position(source_url=<first candidate_url or null>, company_name=<company>, role_title=<role>, profile_slug=<profile>, search_run_id=<search_run_id>, outcome='no-fit', no_fit_reason='snippet-screened: non-tech')`
- Increment `snippet_screened_count`
- Output: `✗ <Company> — <Role> [snippet-screened: non-tech]`
- Continue to next job without fetching the URL

**Judgment rule:** This is a high-confidence signal only. The company + title + snippet must together give no plausible path to a fit under any active profile. When in doubt, proceed to fetch. Examples of clear signals: food/beverage company with "Market Development" role describing regional sales territory management; construction company; pharmaceutical company with no AI/SaaS connection. This formalizes the ad-hoc pre-screening that occurred in the first vendor-gtm run.

**3d. Extract apply links** (for non-duplicate, non-snippet-screened jobs):
- If `candidate_urls` is empty: `fetch_result = "no_url"`, `full_jd_content = null` → jump to **3f (Failure)**

**JD content handling — hard rule:** `full_jd_content` is an in-memory string variable set by this step. Do NOT write it to a temp file (e.g., `/tmp/jd-*.md`, `/tmp/job-description-*.md`). Do NOT issue `cat` commands to display JD content mid-loop. Pass `full_jd_content` directly to `process-jd` as the `jd_content` parameter. No disk I/O for JD text occurs between fetch and `process-jd` handoff.

**3e. Attempt to fetch the full JD:**

Do NOT use `sharing_link` — it is a Google search URL that returns HTTP 500 once the job leaves Google's index.

For each `url` in `candidate_urls` (in order):

- **Try WebFetch first.** If the response title/body contains login-wall signals (`"sign in"`, `"log in"`, `"authwall"`, `"join now"`, `"join to see"`, `"please sign in"`, `"sign in to view"`, `"create an account"`) or the URL contains auth path segments (`signin`, `login`, `signup`, `join`, `authwall`, `challenge`): skip WebFetch, fall through.
- **If WebFetch succeeded:** `fetch_result = "success"`, `full_jd_content = <response body>`, `fetch_url = url` — stop iterating URLs for this job.
- **Fall back to fetch-jd.py:**
  ```bash
  "$PLAYWRIGHT_PYTHON" "$APP_DIR/scripts/fetch-jd.py" --md-out - "<url>"
  ```
  - Exit 0: `fetch_result = "success"`, `full_jd_content = stdout`, `fetch_url = url` — stop iterating
  - Exit 2: auth required — continue to next URL
  - Exit 3: job closed — do NOT create a folder; output: `- <Company> — <Role> [skipped — job closed]`; increment `closed_count`; continue to **next job**
  - Exit 1 or other: `fetch_result = "failed"` — continue to next URL

If all URLs exhausted without success: `full_jd_content = null`

**3f. Failure handling** (when `full_jd_content == null`):

Derive folder slug: `YYYY-MM-DD-<company-slug>-<role-slug>`.

Compose and save a minimal fetch-failed stub:

`notes_content`:
```markdown

**Status:** Pending Review
**Status Detail:** Fetch failed — <fetch_result: "no_url" | "auth_required" | "failed"> — full JD not available
**Source:** SearchAPI / Google Jobs — /ingest <profile>
**Date:** YYYY-MM-DD

## Search Snippet

<If raw.job_highlights present: render each highlight group as subheading + bullets. If absent: "_No highlights available from search result._">

## Next Steps
- [ ] Manually locate apply link and paste JD to continue processing, or re-run /ingest after auth setup
```

`jd_fallback_content`:
```markdown
**Source:** SearchAPI / Google Jobs (full JD fetch failed — <fetch_result>)
**Date:** YYYY-MM-DD

---

# <raw.title> — <raw.company_name>

## Overview

| Field | Value |
|---|---|
| Company | <raw.company_name> |
| Location | <raw.location> |
| Via | <raw.via, or "Not listed"> |
| Employment Type | <raw.extensions.schedule_type or "Not listed"> |
| Salary | <raw.extensions.salary or "Not listed"> |
| Posted | <raw.detected_extensions.posted_at or "Not listed"> |

## Description

<raw.description verbatim, or "_No description available._" if absent>

<For each group in raw.job_highlights (if present): ## <group.title> + bullets>

## Apply Links

<one bullet per apply link; "_No apply links available._" if none>
```

**OB1:**
- `upload_file('applications/<folder>/search-result.json', <raw_json verbatim>, 'application/json')`
- `upload_file('applications/<folder>/notes.md', notes_content, 'text/markdown')`
- `upload_file('applications/<folder>/jd-<company>-<role>.md', jd_fallback_content, 'text/markdown')`

- `log_ingested_position(source_url=<first_url or null>, company_name=<company>, role_title=<role>, profile_slug=<profile>, search_run_id=<search_run_id>, application_id=<new_app_id>, outcome='fetch-failed', no_fit_reason=<fetch_result>)`

**Local:**
- `mkdir "$APPLICANT_DIR/applications/<folder>/"`
- Write `search-result.json` (raw verbatim), `notes.md`, `jd-<company>-<role>.md`

- Append `<first_url or "">,<company>,<role>,<profile>,fetch-failed,<fetch_result>,false,,<now_iso>` to `ingested-positions.csv`; add to in-memory dedup set

- Increment `fetch_failed_count`; append `{company, title, location, reason}` to `fetch_failed_jobs`
- Output: `! <Company> — <Role> [fetch failed — <fetch_result>]`
- Continue to next job

**3g. Process the JD** (when `full_jd_content != null`):

Increment `screened`.

Call workflow `process-jd` with:
- `jd_content = full_jd_content`
- `source_url = fetch_url`
- `source_name = "SearchAPI / Google Jobs — /ingest <profile>"`
- `profile_hint = <profile>` (the profile being searched)

`process-jd` returns `{folder_slug, application_id, verdict, score, profile_match}`.

**After process-jd resolves (both fit and no-fit):**

- **OB1:** `log_ingested_position(source_url=<fetch_url>, company_name=<company>, role_title=<role>, profile_slug=<profile>, search_run_id=<search_run_id>, application_id=<application_id if fit else null>, outcome=<verdict>, no_fit_reason=<score and reason if no-fit>)`

  - No-fit: `- <Company> — <Role> [no fit — score N/10]`

## Rules

- Do not auto-generate resumes. Fit jobs are saved as stubs for the applicant to review.
- Try WebFetch first on each apply URL before falling back to fetch-jd.py. Check for login-wall signals before accepting WebFetch output.
- `search-result.json` is written for every job that gets a folder (fit, no-fit, and fetch-failed).
- Call `log_ingested_position` for EVERY job processed (including duplicates, snippet-screened, and fetch-failed). This is the audit trail.
- The Python script performs only in-run in-memory dedup (duplicate IDs within a single API response). All persistent dedup logic lives in this workflow.
- Do not fabricate company, role, or location data.
- Always pass `--query "<query_for_api>"` to the script — never rely on the script's table-lookup.
- The script auto-detects OB1 mode via `DATA_BACKEND=ob1`; in OB1 mode it skips local profile directory checks and raw-response saves.
- Use `$PLAYWRIGHT_PYTHON` (not system python3) to run the scripts.
- Cross-pass dedup: `check_position_seen` handles cross-pass duplicates automatically. A job that appears in both the onsite pass and the remote pass will be marked `seen=true` on the second encounter and skipped — this is the expected behavior.
