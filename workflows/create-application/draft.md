# Create Application Workflow (draft)

Runs when a job description is provided (URL, document, or paste). All file access follows the storage-routing policy.

**Changes from v4:**
- Step 4b (Company Research thought) removed entirely. Company context — structured reference (products, division, funding) AND market/strategic narrative — is now generated by `process-jd` Step 2.5 (WebSearch) and lives in `job-description.md ## Company & Market Context`. It is available at Pending Review without opening notes.md. notes.md no longer has a ## Company Research section.
- Steps renumbered: former 4c → 4b (Resume Strategy), former 4d → 4c (Update notes-index.md), former 4e → 4d (Generate notes.md).

## Step 0 — Tracker Check + Ingest History

**Tracker check** (unchanged from v3): Check the tracker for a prior application at this company:
1. If exactly one entry exists, proceed with that context
2. If multiple entries exist (different roles or dates), confirm with the user which position is relevant — include "new position" as an option
3. If there is no entry, treat it as a new company/JD to screen

**Ingest history check** (OB1 mode only, after tracker check finds no active entry):

Call `check_position_seen(source_url=<url or null>, company_name=<company if known>, role_title=<role if known>)`.

- `seen=true, outcome='no-fit'`: surface to the user: "Note: this position was previously screened and rejected via /ingest (<first_seen_at>). Proceed anyway?" Continue if the user confirms.
- `seen=true, outcome='fit'`: skip (already in tracker; covered by tracker check above).
- `seen=true, is_repost=true`: note "Repost detected (first seen <first_seen_at>)" and continue.
- `seen=false`: continue normally.

(Local mode: check `ingested-positions.csv` in-memory if already loaded, otherwise skip.)

## Step 1 — Fetch the JD

**Try WebFetch first.** If it returns a login wall (page title/body contains "sign in", "authwall", "join now", etc.) or fails:

1. Fall back to `"$PLAYWRIGHT_PYTHON" "$APP_DIR/scripts/fetch-jd.py" "<url>"`
2. Exit code 2 (auth required): tell the user to run the setup command printed to stderr — do not proceed until they confirm auth is done, then retry. Auth files live in `$APPLICANT_DIR/.auth/`. Re-run `--setup <url>` or `--import <domain>` to refresh expired cookies.
3. Exit code 1 (navigation error): ask the user to paste the JD text directly
4. Exit code 3 (job closed): the posting is no longer available or the position has been filled.
   - Search applications for an existing folder whose slug matches this company and role (fuzzy: lowercase folder name contains the company name and a fragment of the role title)
   - **If an existing application IS found:**
     - Update notes-index.md (or notes.md if legacy): set `**Status:**` to `Closed` and `**Status Detail:**` to `Closed — position no longer available (YYYY-MM-DD)`
     - OB1: `update_application_status(id, 'closed', 'Position closed (YYYY-MM-DD)', null)`; capture `application_event` thought: `"Position confirmed closed via URL fetch — YYYY-MM-DD"`
     - Local: move tracker row to Rejected/Closed; update notes.md status fields
     - Inform the user: "This job posting is no longer available. Application [folder] status updated to Closed."
   - **If no existing application is found:** inform the user: "This job posting is no longer available — position appears closed or filled. No further processing."
   - In both cases: stop — do not proceed with screening or document generation

**PDF and document JDs:** Use `pdftotext` or ask the user to paste if WebFetch fails.

Never stop at a step-1 failure without attempting step 2 of the fallback chain.

## Step 2 — Process JD

Call workflow `process-jd` (pinned version) with:
- `jd_content = <fetched JD text>`
- `source_url = <source URL, or "Pasted" if no URL>`
- `source_name = "Manual"`
- `profile_hint = null` (let jd-evaluation choose the best profile)
- `source_metadata = {}` (no raw search data for manual JDs)

Also pass the pre-extracted criteria context to jd-evaluation (as process-jd's Step 1 requires):
- From `applicant.md`: Location section, Deal-breakers (Hard No), compensation/target salary
- From `PROFILES-QUICK-REFERENCE.md`: Hard Stops, Location Check, all profile slugs

`process-jd` returns `{folder_slug, application_id, verdict, score, profile_match}`.

`process-jd` also:
- Creates `notes-index.md` with header block and thought IDs for `jd_analysis` and `fit_assessment`
- Captures `jd_analysis` and `fit_assessment` thoughts in OB1 (OB1 mode only)

**After process-jd returns — log to ingest audit trail:**
- **OB1:** `log_ingested_position(source_url=<source_url or null>, company_name=<company>, role_title=<role>, profile_slug=<profile_match>, search_run_id=null, application_id=<application_id if fit else null>, outcome=<verdict>, no_fit_reason=<score+reason if no-fit>)`
- **Local:** Append row to `$APPLICANT_DIR/search/ingested-positions.csv` (create with header if missing):
  `<source_url>,<company>,<role>,<profile_match>,<verdict>,,false,,<now_iso>`

## If NO FIT

`process-jd` has already created the no-fit folder with `notes-index.md` (status + fit_assessment thought ID) and updated the tracker. Stop — nothing more to do.

## If FIT (switch to Sonnet)

### Step 3 — Generate Resume

- Read profile content per storage-routing: `profiles/<profile_match>/<profile_match>-CONTENT.md` and `profiles/EXPERIENCE-REFERENCE.md`
- Generate tailored resume via skill `resume-generation` (pinned version)

### Step 4 — Capture Application Thoughts (OB1 only)

Capture the remaining notes sections as OB1 thoughts. Then update notes-index.md with all thought IDs.

**Step 4a — Domain Connection thought**

Perform the four-source domain connection check per policy `company-descriptors` (professional roles, personal/life experience, specific artifacts built, use-case connections).

```
capture_thought(
  content = "<four-source domain connection narrative, 150–400 words>",
  metadata = {
    source_type: "job_search",
    thought_category: "domain_connection",
    application_id: <application_id>,
    application_folder: <folder_slug>,
    company: <company>,
    profile_slug: <profile_match>
  }
)
→ save as domain_connection_thought_id
```

Also store the one-sentence summary in `js_applications`:
```
update_application_fields(
  id = <application_id>,
  domain_connection = "<one-sentence summary from domain connection narrative>"
)
```

**Step 4b — Resume Strategy thought**

Capture the tailoring rationale from the resume generation step.

```
capture_thought(
  content = "<resume strategy, 150–300 words: emphasis priorities, key differentiators for this JD, coverage gaps acknowledged>",
  metadata = {
    source_type: "job_search",
    thought_category: "resume_strategy",
    application_id: <application_id>,
    application_folder: <folder_slug>,
    company: <company>,
    profile_slug: <profile_match>
  }
)
→ save as resume_strategy_thought_id
```

**Step 4c — Update notes-index.md with all thought IDs**

Fetch the current notes-index.md and add thought IDs for the new sections:
```
get_file('applications/<folder_slug>/notes-index.md')
→ append to ## OB1 Thought Keys:
  - domain_connection: <domain_connection_thought_id>
  - resume_strategy: <resume_strategy_thought_id>
upload_file('applications/<folder_slug>/notes-index.md', <updated content>, 'text/markdown')
```

**Local mode — Step 4 equivalent:**

Expand the `notes.md` stub (from process-jd/v1 local path) into the full structure per `v3.md` Step 4 (domain connection, resume strategy). No company_research section — company context is in job-description.md. No thought capture in local mode.

### Step 4d — Generate notes.md (OB1 only)

Call skill `application-summary` (pinned version) with `application_folder = <folder_slug>`.

This generates the full `notes.md` from the 4 thoughts captured so far (jd_analysis, fit_assessment, domain_connection, resume_strategy) and uploads it to OB1. The review-before-PDF gate is unchanged — `notes.md` exists at this point.

### Step 5 — Update Tracker

`update_application_status(id, 'resume-ready', 'Resume generated [YYYY-MM-DD] — not yet submitted', null)` or update Active Applications row.

### Step 6 — Present for Review

Present the generated resume and the notes.md (generated in Step 4e) for user review.

**After the user submits:** Run `/audit [folder-name]` to verify completeness, then `/apply "Company" "Role" "date"` to record the submission in both the tracker and notes-index.md atomically.

## Status Changes — Two-File Rule

**Any status change** (submission, withdrawal, rejection, closing, deciding not to pursue) must update **both**:

1. The tracker (or `js_applications` via `update_application_status`)
2. `applications/<folder>/notes-index.md` — update the `**Status:**` and `**Status Detail:**` fields to match

**Status field schema (both files):**
- `**Status:**` — one of 9 canonical values: `Pending Review` | `Resume Ready` | `Applied` | `Interview scheduled` | `Interviewed` | `Exercise/Test requested` | `Exercise/Test` | `Offer` | `Closed`
- `**Status Detail:**` — free text: dates, flags, recruiter names, context

For applications created before this workflow version (with `notes.md` but no `notes-index.md`): apply the two-file rule to `notes.md` using the v3 protocol.

**Submission recording:** Do NOT create a `## Submission Log` section. Capture an `application_event` thought (OB1 mode) with content `"Applied via [portal] ([URL]); resume: [filename].pdf — YYYY-MM-DD"`. Update `**Status:**` in notes-index.md and append to `## Application Log` in notes.md (if it exists).

## JD Regeneration (Existing Applications)

When regenerating `jd-*.md` and/or `job-description.md` for an existing application folder:

1. After writing the updated files, compare the new `job-description.md` fit assessment against the current notes-index.md `**Status:**` and the tracker row.
2. If the new data reveals a status change — confirmed hard stop, closed posting, passed deadline, domain mismatch, or materially changed fit score — apply the two-file rule immediately.
3. Do not close the regeneration task without checking for status drift.

## notes-index.md Status Tracking

`notes-index.md` is the **primary** status-bearing file for new applications (v4 workflow). The full notes.md generated by `application-summary` mirrors status fields but is not the source of truth. When regenerating notes.md, always pull status from `get_application(id)` (OB1) or notes-index.md (local), not from the prior notes.md.

## Full notes.md Structure (for reference — generated by application-summary)

Every `notes.md` generated from thoughts must include a Table of Contents and all required sections in order. See `skills/application-summary` for the rendering spec.
