# No OB1 Edits Policy

## Rule

Never modify files in the local OB1 checkout (the OB1 repo directory, or any path inside it) for job-search purposes. The OB1 repo is an independent open-source project. Job-search tooling is a consumer of OB1, not a contributor to it.

**All** functionality that supports job-search operations — MCP tools, output formatting, database queries, workflow helpers — must be implemented in the job-search repo at `$APP_DIR/integrations/ob1/`.

## Why

In June 2026, a session added thought ID output to OB1's `search_thoughts` and `list_thoughts` MCP tools by editing files in the OB1 repo checkout (`integrations/kubernetes-deployment/index.ts` and `server/index.ts`). This was wrong because:

1. **OB1 is not the job-search repo.** Changes in OB1 affect the general-purpose thought system, not just job-search. They create coupling between two independent codebases.
2. **OB1 changes bypass job-search review, versioning, and the skill/policy system.** They are invisible to `/context`, skill docs, and the registry.
3. **OB1 changes are hard to trace.** A future session will see OB1 behaving differently and not know why — there's no job-search CLAUDE.md, policy, or memory in the OB1 repo.
4. **The correct extension point already exists.** The job-search MCP server in `$APP_DIR/integrations/ob1/job-search-tools.ts` is a parallel server that shares OB1's database. New tools, output changes, and query logic belong there.

## How to apply

When a session is about to write to, edit, or commit to any file in the local OB1 repo checkout:

1. **Stop immediately.** Do not make the edit.
2. Ask: "Can this be implemented in `$APP_DIR/integrations/ob1/job-search-tools.ts` or `job-search-server.ts` instead?"
3. If yes: implement it there. The job-search MCP server can query OB1's PostgreSQL database directly (`thoughts`, `edges`, `entities` tables) — no OB1 server change is needed for new query patterns.
4. If the user explicitly asks to change OB1 for a general OB1 improvement (not job-search): confirm with the user that this is intentional and is for OB1 itself, not for job-search support. Then and only then proceed.

## Scope

This policy covers:
- Any file in the local OB1 repo checkout
- Any Docker image built from the OB1 repo that is patched for job-search purposes
- Any k8s manifest changes committed to the OB1 repo for job-search purposes

It does NOT prohibit:
- k8s manifests in `$APP_DIR/integrations/ob1/k8s/` that configure OB1's deployment (those are in the job-search repo)
- Reading OB1 source code for reference
- Reverting OB1 changes that violated this policy
